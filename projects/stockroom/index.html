A small task, followed through.

My warehouse jobs gave me a familiar task to model: finding boxes, loading a cart, and handling a shortage. Stockroom is a practice app for that workflow, using fictional products and orders.

This page shows the local app. You can run it from the public repository using the setup steps in its README.

See the workflow.

These screenshots were taken from the running app on September 24, 2026. They show sample states; they are not a continuous recording.

1. Pick what is available.

The order board shows new, ready, loaded, and shortage states. In this sample, an order needs 12 trail mix cartons and only 8 have been picked. The missing four remain visible. An order can be loaded only after all its boxes are picked.

2. Request a recount.

A worker asks for a stock change and gives a reason. The shelf count stays unchanged while the request is pending. A manager must approve it. If the stock changed after the request, the app asks for a fresh count.

3. Keep a record of the change.

The activity list records the account, action, and time. Picking stock, creating an order, and loading it leave separate entries so the sequence can be checked.

How the parts fit.

React and TypeScript
Build the forms, order cards, stock table, and activity view. The browser sends requests to the Java API.
Java and Spring Boot
Validate requests, check worker and manager roles, and apply the order rules. Spring JDBC sends explicit SQL to PostgreSQL.
PostgreSQL
Stores orders, products, adjustments, and activity. Transactions keep stock counts and order lines together. Row locks prevent two picks from taking the same stock.
Docker and GitHub Actions
Build the frontend and Java service, start a separate test database, and run real HTTP checks.

Rules behind the screen.

A repeated request should not pick twice.

A request key identifies one action. Repeating the same request returns the saved order. Reusing the key for a different action returns a conflict.

An old page should not overwrite a newer order.

Each order has a version counter. A write using an old version is rejected, so the page can refresh before trying again.

Stock and the pick list must agree.

The server locks products in a consistent order. It changes the shelf count, picked quantity, order state, and activity record in one transaction.

Builds and checks that ran.

The 14 HTTP/database checks cover sign-in, CSRF protection, manager approval, shortages, duplicate requests, stale versions, invalid quantities, and concurrent picks.

On September 24, 2026, the Docker build and test workflow passed on GitHub. The build checks TypeScript and produces the frontend files. Integration checks use a separate PostgreSQL database.

Scope and learning.

The accounts are fixed demo roles. There is no barcode hardware, shipping integration, account registration, or production deployment. This is not software used by a former employer.
